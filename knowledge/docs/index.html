Build readiness

Build readiness

Catches the decisions a change still needs before the build starts, asks the user to make them in one batch, and keeps a per-change record of every decision until it is settled.

How it works, roughly`/kit:ready` reads a planned change the way the builder will and lists gaps, differences, points to confirm and new tools, asked in one batch. Answers, and items put off as "Later", go into the change's `decisions.md`, which only a script writes.

Readiness check

The readiness check SHALL run for one OpenSpec change whose planning artifacts are complete. It SHALL read the change's proposal, specs, design and tasks, and the PRD the proposal links to, if any. It SHALL list:

  • gaps: behaviors with no scenario (empty, error, loading, permission and limit cases, UI states and copy, data shape), and vague or unfinished wording (TBD, TODO, "etc.", "fast", "nice", question marks in requirements);
  • differences: places where the PRD, the specs and the design disagree;
  • points to confirm: key assumptions and high-impact behaviors that look decided but that the user should check;
  • new tools: dependencies the change plans to add (see "New-tool check").

Each item SHALL say where it was found. The check SHALL NOT edit the change's artifacts unless the user picks an answer for that item.

Decisions asked in one batch

The readiness check SHALL show its items before anything else, with their count. Each item SHALL be offered as a question with two to four options, one marked as recommended, and SHALL always allow "Later". The questions SHALL be asked together, not one at a time during the build. When the user picks an answer, the agent SHALL write it into the change: a behavior as a spec scenario, a decision with its reason into design.md. When the user picks "Later", nothing in the change SHALL be edited for that item.

Readiness never blocks

The readiness check SHALL only warn. It SHALL end by saying the build can go ahead, and how many decisions are still open. No kit hook or skill SHALL stop /opsx:apply because of the readiness check or open decisions.

Decision record

Each change SHALL have at most one decision record, decisions.md in the change folder, created on first use. Entries SHALL be added and updated only through the kit's script, never by hand. Each entry SHALL have:

  • an id;
  • a kind: gap, difference, confirm, new-tool, unplanned-tool, behavior, or decision;
  • the question or finding, and where it came from;
  • the options and the recommended one, when there are options;
  • a status: open, decided or later;
  • the answer and where it was written, once decided;
  • the date of each change of status.

later SHALL count as open everywhere open decisions are counted.

New-tool check

The readiness check SHALL compare the tools the change plans to add (from its design and tasks) with the project's existing dependencies (package.json dependencies and devDependencies). For each planned tool, it SHALL say whether an existing dependency already covers the same purpose, and SHALL offer to reuse it (recommended when one exists) or to add the new one. A tool kept as new SHALL have its reason written into design.md. A project without package.json SHALL get a one-line note that the tool check was skipped.

Docs sync

Docs sync

Brings a change's specs and design up to date with what was actually built, before archive turns them into the project's living record, and asks the user about built behavior that may not be what they want.

How it works, roughlyRuns inside `/kit:verify`, before archive. It reads the build's apply receipt, the commits since the docs were last edited, the diff and dependency changes, sorts each item (behavior, decision with depth, how the build ran), and writes only what you say yes to.

Docs sync sources

The docs sync SHALL run as part of the verify step for one change. It SHALL gather:

  • the decisions the build recorded, from the change's apply receipt (apply.md) when one exists;
  • the commits since the change's artifacts were last edited, with a count of the code commits among them;
  • the change's diff;
  • dependencies added or removed in package.json since the change started.

When the artifacts were last edited before code commits were made, the report SHALL say so, with the date and the count.

Changed by build-readiness · 2026-10-12
  1. 1Docs stopped early
    GIVENa change whose `design.md` and specs were last committed on 2026-10-10, followed by 29 code commits
    WHENthe docs sync runs
    THENit reports "docs last updated 2026-10-10; 29 code commits since"
  2. 2No apply receipt
    GIVENa plain OpenSpec change with no `apply.md`
    WHENthe docs sync runs
    THENit works from the commits and the diff alone, and says the apply receipt was missing

Sort what was built

The docs sync SHALL sort each item it finds into one of:

  • behavior: something the user can observe. It SHALL be proposed as a spec scenario in the change's delta specs (Given/When/Then);
  • decision with depth: a choice that trades something, shapes more than one behavior, or would surprise someone later. It SHALL be proposed for design.md, with its reason;
  • how the build ran: process detail such as push cadence, task dispatch or test ports. It SHALL NOT be proposed for the docs, and SHALL be listed in one line as left out.

A small or preference decision SHALL NOT be proposed for design.md just to give it a reason.

Every apply-receipt item SHALL end up either proposed or left out. An item under the receipt's "Visible changes" SHALL be treated as a behavior, never left out. The verify script SHALL refuse a docs-sync summary whose proposed and left-out counts don't cover every receipt item.

Changed by build-readiness · 2026-10-12
  1. 1Behavior found in the receipt
    GIVENthe apply receipt says "Fit on a single sticky zooms close to 350%" and no scenario covers fitting one item
    WHENthe docs sync runs
    THENit proposes a scenario for fitting a single item under the fit requirement
  2. 2Process ruling left out
    GIVENthe apply receipt says "the speed test runs its own dev server on port 3101"
    WHENthe docs sync runs
    THENthe item is listed as left out (how the build ran), and nothing is proposed
  3. 3Receipt item not sorted
    GIVENthe apply receipt has 20 items
    WHENthe agent records a docs sync with 10 proposed and 6 left out
    THENthe script stops and says that 4 receipt items aren't sorted, and nothing is recorded

Flag built behavior that may be unwanted

The docs sync SHALL flag an item when the built behavior changes what the user sees in a way the specs did not plan, or when it could lose or hide the user's data. A flagged item SHALL be asked as "this is what was built; is it what you want?", with options to keep it (then documented as is) or to change it (then recorded as an open decision and not documented as final).

    GIVENthe build loads a corrupt saved board as an empty board
    WHENthe docs sync runs
    THENthe item is flagged and asked before any spec text is written for it

Unplanned dependencies

The docs sync SHALL list each dependency added during the change that the change's proposal, design and tasks do not mention, and SHALL ask whether to keep it. A kept one SHALL get its reason written into design.md. Removed dependencies SHALL be listed for information.

Updates only on a yes

The docs sync SHALL propose each update, show the text it would write and where, and SHALL write it only after the user says yes to that item. Each item SHALL be recorded in the change's decision record with its outcome. The docs sync SHALL be advisory: it SHALL NOT add a HARD item to the verify report.

Flow recommendation

Flow recommendation

Recommends plain OpenSpec or SuperSpec for a change from a short risk checklist, with the reasons shown, so the user decides with evidence instead of the agent's gut feeling.

Risk checklist

The kit SHALL score a change description (the PRD and/or the proposal text) against a risk checklist:

  • touches payments, money or billing;
  • touches authentication, sessions or permissions;
  • touches personal data;
  • includes a data migration or a schema change;
  • is hard to undo (deletes data, irreversible operations);
  • has a wide reach (many areas or modules named);
  • is vague (open questions or "unknown" left in the PRD).

It SHALL report which items matched, with the words that matched.

Changed by quality-gates · 2026-10-07
  1. 1Risky change
    WHENthe description says "add Stripe payments and migrate the orders table"
    THENthe matches are payments and data migration, each with the matched words

Flow recommendation

The kit SHALL recommend SuperSpec when two or more checklist items match, or when payments, authentication or a data migration matches. Otherwise it SHALL recommend plain OpenSpec. The recommendation SHALL show its reasons, and SHALL be offered at proposal time. The user decides, and the agent SHALL NOT switch flows on its own.

Changed by quality-gates · 2026-10-07
  1. 1Small change
    WHENthe description is "add a dark mode toggle to settings"
    THENthe recommendation is OpenSpec, with "no risk items matched"
  2. 2User decides
    WHENSuperSpec is recommended and the user chooses OpenSpec
    THENthe change proceeds with OpenSpec, and no SuperSpec tools are added

Labelled eval set

The flow recommendation SHALL be tested against a set of at least ten labelled example descriptions, each marked with the expected flow, and SHALL match every label.

  1. 1Eval set passes
    WHENthe evals run
    THENevery labelled example gets its expected flow

Knowledge capture

Knowledge capture

Gives each project one plain-Markdown home for its context (notes, PRDs, assets), and lets the user capture a note by voice or text in seconds without any external service.

Knowledge folder layout

A project's knowledge folder SHALL default to knowledge/ at the project root, and its location SHALL be configurable per project. It SHALL contain:

  • notes/
  • prds/
  • assets/
  • archive/

Notes MAY be grouped in topic subfolders under notes/. Kit skills SHALL read notes/ recursively and SHALL NOT read anything under archive/.

Note format

Each note SHALL be one Markdown file named <YYYY-MM-DD>-<slug>.md, where the slug comes from the title. Its frontmatter SHALL include:

  • title and date (required)
  • tags (optional list)
  • source (optional: voice, text, or a pointer such as a URL or a path)

Two notes with the same date and slug SHALL NOT overwrite each other. The second one gets a numeric suffix.

Capture a note

The capture skill SHALL save the user's text (typed, dictated with /voice, or pasted) as a note. If the user gives no title, the skill SHALL propose one from the content and use it only after the user confirms or edits it. When the user names a topic, the note SHALL go into that topic folder under notes/, which is created if missing. A pointer note (a URL or a path to content stored elsewhere) SHALL record the pointer in source and SHALL NOT copy the pointed-to content.

PRD authoring

PRD authoring

Turns a project's notes into a PRD that the user owns and edits freely, and hands a Ready PRD to OpenSpec planning with a record of exactly which version was planned.

PRD format and status

Each PRD SHALL be one Markdown file in prds/, named <slug>.md. Its frontmatter SHALL include:

  • title
  • status: one of Draft, Review, Ready, Building, Shipped
  • sources: a list of note paths relative to the knowledge folder (may be empty)
  • change: the name of the OpenSpec change that uses it, once one exists

The body SHALL follow the kit's PRD template, written in the kit's own words. Licensed PM-OS text SHALL NOT be copied into it. The template's requirements section SHALL ask for user stories in Given/When/Then form (a starting state, an action, an expected outcome), grouped by flow or screen. The PRD skill SHALL draft requirements in that form, and SHALL keep a short plain statement where a requirement has no meaningful starting state or action.

When a draft or an update leaves items under Open questions, the PRD skill SHALL keep them out of its end report and SHALL ask, as a separate step, whether to go through them now or later. Now: it SHALL ask each question with concrete options, its recommendation first, and a Later option, and SHALL write each answer into the PRD. Later: it SHALL write nothing, and the questions SHALL stay in the Open questions section.

It SHALL draft the PRD only from the notes the user picks, and SHALL cite each one in sources. Information that is not in the picked notes or the user's prompt SHALL be marked as an assumption or an open question, never stated as fact.

When a PRD's status is Ready, the project's routing rules SHALL direct the proposal step to read that PRD as its main input. The resulting proposal SHALL record the PRD's path and the commit it was read at. The PRD's change field SHALL be set to the new change's name, and its status SHALL move to Building only after the user confirms.

Status changes need the user

The kit SHALL NOT change a PRD's status, or any other content, without the user's confirmation. A suggested status change, for example Shipped after the change is archived, SHALL be offered and applied only on a yes.

Changed by prd-pipeline · 2026-10-07

    WHENthe change named in a `Building` PRD is archived

PRDs ordered by most recent update

Wherever the kit lists PRDs or asks the user to choose one, it SHALL order them by when they were last updated, newest first. This covers the knowledge listing, the PRD skill, and the proposal step's choice between several Ready PRDs. A PRD's last update is:

  • the file's modification time, when it has uncommitted changes or is not tracked by git;
  • otherwise, the time of the last commit that touched it;
  • the file's modification time, when git is not available.

Ties are broken by slug.

Project starter

Project starter

Sets up a new or empty project with the kit's basics in minutes instead of half a day, driven by the registry, safe to re-run, and never destructive to existing project files.

How it works, roughlyPlan first, then apply: the starter works out the files, tools and diffs, asks one question (the project type) and one yes, then writes. In `CLAUDE.md` and `.gitignore` the kit owns only the text between its own markers.

Tools are applied by tier

The starter SHALL ask for the project type (or accept it as an argument). Among registry entries with scope project and status adopted or trial, it SHALL select tools by tier:

  • global: applied to every project the kit sets up
  • project: not asked about and not applied at setup; listed in the summary as available on demand, and applied only when the user explicitly asks for it (for example when a change needs it)
  • project-type:<type>: applied only when that type is selected

Entries with status dropped or later SHALL NOT be applied or offered. The summary SHALL list each selected tool and why (its tier).

Project tools are installed per project

The starter SHALL install the selected tools (plugins, MCP servers, skills) for this project only, and SHALL NOT enable or configure them at user level or in a tool's global configuration. It SHALL change only the settings entries it manages, leaving other settings in the project's files untouched. When a tool's install needs the user (for example an OAuth sign-in), the starter SHALL stop at that step, tell the user exactly what to do, and report the tool as pending rather than as installed.

Setup asks one question

The starter SHALL ask only one question: the project type. Each type option SHALL show the tools it adds. When the project's files make a type likely, that type SHALL be recommended first, with the reason. Otherwise "none" is offered first.

The starter SHALL NOT ask about opt-in (project-tier) tools. It SHALL list them once in its summary as "available on demand", each with its one-line description. They are added later, when a change needs them.

Global and type tools SHALL be installed without further questions. Steps that need the user (for example a sign-in) SHALL be listed as the user's steps, as before.

Changes to existing files SHALL be shown with their diff, a one-line description and a recommendation, and confirmed together with one yes. The user MAY exclude any of them, and nothing SHALL be applied without that yes.

Setup summary in three parts

The starter's summary SHALL have three parts:

  • Done: what was written, installed or already in place.
  • Needs you: only steps that block using the project now. Ideally there are none.
  • Later: steps that matter only when a tool is first used (for example a tool's own init command), each phrased as "when you first <do X>".

An item SHALL appear in only one part. Wording SHALL be written for the user; internal notes (such as unverified install details) SHALL NOT be shown.

Quality gates

Quality gates

Checks a change before it is closed, sized to the project: hard failures (failing tests, secrets, high-severity security findings) block, everything else is reported as advice the user decides on.

How it works, roughly`/kit:verify` runs the project's tests by its type's policy, `/security-review`, `/code-review`, a changed-files-without-tests check and the docs sync, and writes `verify.md`. A kit hook blocks `openspec archive` until that report passes or is overridden with a reason.

Verify a change

The verify step SHALL run for one OpenSpec change and SHALL produce a report at <change folder>/verify.md. The report SHALL include:

  • the date and the commit it ran at;
  • the test commands it ran and their result;
  • the findings recorded from /security-review and /code-review on the change's files;
  • a docs-sync section: when the docs were last updated and the code commits since, the items proposed, written, declined or left out, and unplanned dependencies;
  • the number of open decisions in the change's decision record, and the date of the oldest;
  • every result marked HARD or ADVISORY;
  • an overall result: pass, fail or overridden.

The test commands come from the project type's test policy (see the toolkit-registry requirement). The security and code reviews are run by the agent in the session, and their findings are recorded through the verify script, never typed into the report by hand. The docs-sync section and open decisions SHALL be ADVISORY.

If the change already has a verify.md the kit didn't write, verify SHALL keep it as verify-earlier.md instead of overwriting it, and SHALL list it as an ADVISORY item.

Changed by build-readiness · 2026-10-12
  1. 1All green
    WHENthe policy's tests pass and the reviews record no high-severity finding
    THEN`verify.md` has result `pass`, and lists any advisory items
  2. 2Failing test
    WHENa test command required by the policy exits non-zero
    THEN`verify.md` has result `fail`, with a HARD item naming the command and the end of its output
  3. 3Docs sync with open items
    GIVENthe tests pass, and the docs sync leaves one flagged item open
    WHENverify finishes
    THENthe result is `pass`, and the advisory list shows the docs-sync summary and "1 decision still open"
  4. 4Earlier report from another tool
    GIVENthe change has a `verify.md` written by SuperSpec
    WHENverify runs
    THENthat file is renamed to `verify-earlier.md` unchanged, and the report lists it as an advisory item to read

Hard failures and overrides

A failing required test command, a required test command that is missing (where the policy requires one), and a high-severity security finding SHALL be HARD. Everything else (changed files without tests, review comments, lower-severity findings, browser checks) SHALL be ADVISORY. A HARD item SHALL block until it is fixed and verify passes on a re-run, or until the user overrides it. An override SHALL record the user's reason and the date in the report, and SHALL set the result to overridden. The agent SHALL NOT override on its own.

When the archive goes ahead and the change has open decisions, the gate SHALL tell the agent how many are open and since when, so it can tell the user, and SHALL NOT block for them. Skill evals

Skill evals

Makes "this skill or tool works" a measured result instead of a feeling: every kit skill ships fixed test cases, and results feed registry verdicts and A/B tool trials.

How it works, roughlyEach kit skill has `evals/<skill>/cases.yaml`. Script checks run for real in a temporary sandbox; judgment checks are scored per named criterion. Every run is saved, so runs can be compared.

Every kit skill has eval cases

Each skill shipped by the kit SHALL have at least one eval case. Each case defines an input or setup, the expected outcome, and how the outcome is checked. Checks SHALL be automatic wherever the outcome can be checked deterministically (files exist, commands succeed, content matches).

Judgement checks use an explicit rubric

Where an outcome needs judgement (e.g. the quality of a review or document), the eval case SHALL define a written rubric with named criteria. The result SHALL record a pass/fail per criterion, not only an overall score.

Skill routing

Skill routing

Makes it predictable which tool or skill handles each phase of work, so overlapping tools don't compete, and tells the user what to do next without memorising hundreds of skills.

How it works, roughlyThe lane map gives each workflow phase exactly one owning tool, worked out from the registry. `/kit:next` reads the project's PRDs and OpenSpec state and names the next step with its owner.

Lane map derived from registry

The kit SHALL produce a lane map (each workflow phase to exactly one owning tool) from the registry's phase ownership data, among entries with status adopted or trial. For each phase it SHALL show the skill or command to use, when the registry records one. Phases without an owner SHALL be listed as unowned.

The owner SHALL be chosen as follows: 1. A tool that lists another claimant of the phase under overlaps defers to it, and is shown as an alternative for that phase. 2. Among the remaining claimants, an adopted tool wins over a trial tool. 3. If more than one claimant still remains, the phase SHALL be shown as a conflict naming those tools. No owner is guessed.

Changed by kit-local-mvp · 2026-10-07
  1. 1Complete lane map
    WHENthe lane map is generated from a valid registry
    THENevery defined phase shows exactly one owner, or is marked unowned or as a conflict
  2. 2Deferring tool shown as alternative
    WHENOpenSpec (adopted) and SuperSpec (trial) both claim phase `build`, and SuperSpec lists OpenSpec under `overlaps`
    THENOpenSpec owns `build` with its recorded skill, and SuperSpec is shown as the alternative for `build`
  3. 3Tie reported as conflict
    WHENtwo adopted tools claim the same phase and neither lists the other under `overlaps`
    THENthe lane map shows that phase as a conflict naming both tools, with no owner

Projects receive routing rules

When a project is bootstrapped or re-synced, the kit SHALL write routing rules derived from the lane map into the project's agent instructions. The rules state which skill to use for each phase and which overlapping skills not to use. User-written instructions SHALL be preserved.

Tool setup

Tool setup

One command brings a machine up to the kit's toolset, driven by the registry and safe to re-run, so starting or resuming a project never begins with manual installs.

One command installs the machine toolset from the registry

The setup command SHALL check every registry entry with status adopted or trial and scope machine, and SHALL install each missing one using the entry's install instructions. Entries with status dropped or later SHALL NOT be installed. It SHALL end with a summary listing each entry as installed, already present, or failed.

Changed by kit-local-mvp · 2026-10-07
  1. 1Fresh machine
    WHENsetup runs on a machine where none of the machine-scope tools are present
    THENeach adopted or trial machine-scope tool is installed and the summary lists it as installed
  2. 2Dropped tool not installed
    WHENa machine-scope registry entry has status `dropped`
    THENsetup does not install it and does not list it as missing

Setup is idempotent

Running setup again with no registry change SHALL install nothing and SHALL report that nothing needs to be done.

Changed by kit-local-mvp · 2026-10-07
  1. 1Second run
    WHENsetup runs twice in a row
    THENthe second run reports every entry as already present and changes nothing

Installs are confirmed and failures are isolated

Before installing, setup SHALL list what it will install and wait for confirmation. A failed install SHALL be reported with the error and a suggested fix, and SHALL NOT stop the remaining installs.

Changed by kit-local-mvp · 2026-10-07
  1. 1One install fails
    WHENthe install of one tool fails and two others are pending

Toolkit registry

Toolkit registry

A single source of truth listing every tool the kit knows about: why it is there, how it scored, what it costs, which phase it owns and its current verdict. Other kit capabilities read from it.

Registry entries carry required fields

Each registry entry SHALL include:

  • name
  • source (where it installs from)
  • tier: global, project or project-type:<type>
  • reason (why it is in the kit)
  • cost: free, free-tier, paid or uses-claude-quota
  • status: trial, adopted, dropped or later
  • rubric notes covering problem fit, overlap, context cost, run cost, trust, reversibility and license
  • reviewed version and review date
Changed by kit-local-mvp · 2026-10-07
  1. 1Complete entry passes validation
    WHENthe registry contains an entry with every required field filled
    THENvalidation reports the entry as valid
  2. 2Missing field is reported
    WHENan entry lacks a required field (e.g. `reason`)
    THENvalidation fails and names the entry and the missing field
  3. 3Invalid enum value is reported
    WHENan entry has `status: maybe`
    THENvalidation fails and lists the allowed status values

Registry records verdict history

Each entry SHALL keep an ordered history of verdicts. Each verdict records its date, the resulting status, a short rationale, and optionally a reference to the eval results that support it. Existing history entries SHALL NOT be rewritten when a new verdict is added.

Changed by kit-local-mvp · 2026-10-07
  1. 1New verdict appended
    WHENa trial ends and a verdict is recorded for a tool
    THENthe verdict is appended to that tool's history and the entry's status matches the latest verdict
  2. 2Status without supporting verdict
    WHENan entry's status differs from its latest verdict's status
    THENvalidation fails and reports the mismatch

Registry declares phase ownership

Entries MAY declare the workflow phases they own, for each owned phase the skill or command to use, the skills of theirs that are skipped, and the tools they overlap with. Validation SHALL fail when two adopted or trial entries own the same phase without an overlap resolution recorded on at least one of them.

Changed by kit-local-mvp · 2026-10-07
  1. 1Unresolved phase conflict
    WHENtwo adopted tools both declare ownership of phase `plan` and neither records the overlap
    THENvalidation fails and names both tools and the phase
  2. 2Resolved overlap passes
    WHENtwo tools touch the same phase and one lists the other under `overlaps` with the conflicting skill under `skip_skills`
    THENvalidation passes

Entries declare how to check and install

Each entry with status adopted or trial SHALL declare:

  • a scope: machine (installed once per machine: command-line tools, the kit plugin, plugin marketplaces) or project (enabled per project by the starter)
  • a check that tells whether the tool is present
  • install instructions for the supported platform

Validation SHALL fail when an adopted or trial entry lacks any of these, or has a scope value other than machine or project.

Changed by kit-local-mvp · 2026-10-07
  1. 1Missing install data
    WHENan adopted entry has no check or no install instructions
    THENvalidation fails and names the entry and the missing field
  2. 2Later entry without install data
    WHENan entry with status `later` has no install instructions
    THENvalidation passes for that entry

Registry is human-readable and hand-editable

The registry SHALL be a single plain-text file in the kit repository that a person can read and edit in any text editor, and SHALL be validated by one command that exits non-zero on any error.

Changed by kit-local-mvp · 2026-10-07

The registry SHALL define, for each project type (and for none), a test policy:

The registry validator SHALL reject a policy that names an unknown project type, or that has no commands.

Foundations

Technical choices that shape more than one sub-feature, in plain language.

Notes, PRDs and docs are Markdown in the project repoapp-wide

In short
Ideas, notes, PRDs and the living docs live as Markdown files in each project's `knowledge/` folder, in git.
Why (evidence)
Notion was tried first as the PRD store; on the free plan its query limit hit after about 10 calls. Markdown in git needs no MCP server and has no limits (roadmap drift log, 2026-10-06).
Gives you
No external service, no quota, history in git, and files the agent can read directly.
Limits you
No shared web editor or comments outside git.
Affects
knowledge-capture, prd-authoring, the docs page.
History
2026-10-06: Notion dropped; Markdown in `knowledge/` adopted (prd-pipeline).

Tools are enabled per project, never globallyapp-wide

In short
Only the kit, CLIs and marketplaces are global. Workflow plugins, MCP servers and tool configs are switched on per project.
Why (evidence)
You work in repos you don't own; tools must be active only where the kit set the project up. Decided 2026-09-29, after a Superpowers install defaulted to user scope (kit-local-mvp D14).
Gives you
Nothing the kit adds leaks into other repos.
Limits you
Each project installs its own tools. `claude plugin install` defaults to user scope, so the kit always passes `--scope project`.
Affects
project-starter, tool-setup, quality-gates (the hooks do nothing outside kit projects).
History
2026-09-29 kit-local-mvp: decided by the user.

The kit's scripts use no dependenciesapp-wide

In short
Everything under `plugins/kit/` runs on Node's built-ins only. The one package the repo has (`yaml`) is dev-only.
Why (evidence)
The kit is installed once per machine and must work in every project with nothing to install. The registry is YAML for people and JSON for scripts (kit-local-mvp D2); PRD frontmatter uses a small parser instead of a YAML library (prd-pipeline D3).
Gives you
Install and update with no `npm install`.
Limits you
The kit's own small parsers (frontmatter, `spec.md`, the tools inventory) read only simple shapes; anything else is reported, not guessed.
Affects
toolkit-registry, prd-authoring, knowledge-capture, the docs page.
History
2026-09-29 kit-local-mvp: chosen with the registry design.
